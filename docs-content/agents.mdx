## What are FRIDAY Agents?

In traditional systems, you run scripts manually. In FRIDAY, you talk to Agents. An Agent is an autonomous system powered by **LangGraph** paired with a defined set of **tools** exposed via the **Model Context Protocol (MCP)**. The agent reads your intent, selects the right tools, executes them, and feeds results back into the conversation loop until the goal is achieved.

---

## The ReAct Loop

```
User → "Move all delayed tasks to the backlog"
  ↓
RAG Node: Fetch relevant project history and documentation context.
  ↓
Agent Node (Reason): Which tasks are delayed? What does "move to backlog" mean?
  ↓
Tools Node (Act): calls getIssues({ status: "IN_PROGRESS", overdue: true })
  ↓
Agent Node (Observe): receives 3 issues
  ↓
Tools Node (Act): calls updateIssue({ ids: [...], status: "TODO", sprintId: null })
  ↓
Agent Node (Observe): success → respond to user
```

The loop is managed by **LangGraph**, ensuring state is maintained between tool calls and reasoning steps.

## The `/api/mcp` Route

FRIDAY exposes a **live MCP endpoint** at:

```
POST /api/mcp
```

This route implements the full **Model Context Protocol** — it can be connected to any MCP-compatible AI client (Claude Desktop, Cursor, or a custom agent).

### Available MCP Tools

| Tool | Description |
|---|---|
| `getIssues` | Fetch issues with filters (status, priority, sprint) |
| `createIssue` | Create a new issue in a project |
| `updateIssue` | Update an existing issue's properties |
| `assignIssue` | Reassign an issue to a specific user |
| `getSprintData` | Fetch current and upcoming sprint details |
| `searchIssues` | Semantic/Full-text search across all issues |
| `getTeamWorkload` | Analyze team capacity and issue distribution |

<Callout type="warning">
  Tools like `createIssue`, `updateIssue`, and `assignIssue` are marked as **Destructive**. The agent runtime requires explicit UI confirmation before these actions are finalized.
</Callout>

### Connecting an External MCP Client

To connect Claude Desktop or a custom agent to your FRIDAY instance:

```json
// claude_desktop_config.json
{
  "mcpServers": {
    "friday-pm": {
      "command": "node",
      "args": ["-e", "require('http').get('http://localhost:3000/api/mcp')"],
      "env": {
        "FRIDAY_API_URL": "http://localhost:3000"
      }
    }
  }
}
```

Or send raw HTTP requests:

```bash
curl -X POST http://localhost:3000/api/mcp \
  -H "Content-Type: application/json" \
  -d '{
    "tool": "getIssues",
    "arguments": { "status": "BLOCKED", "limit": 10 }
  }'
```

<Callout type="tip">
  The MCP route does not require authentication in development mode. In production, attach a `Bearer` token using your FRIDAY_MCP_SECRET environment variable.
</Callout>

## AI Copilot (Command Center)

The **Friday AI Copilot** in the Command Center is a conversational interface backed by:

1. **Live project context** — blocked issues, overdue tasks, team capacity, sprint status
2. **Your local LLM** — powered by Ollama (`llama3` by default, configurable via `OLLAMA_MODEL`)
3. **Fallback responses** — if the LLM is unavailable, structured fallback messages are shown

To change the model:

```bash
# .env.local
OLLAMA_MODEL=mistral
```

To use an OpenAI-compatible API instead:

```bash
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-4o
```

## Multi-Agent Orchestration

For complex tasks like sprint planning or health audits, FRIDAY uses an **Orchestrator** pattern. This coordinates specialized sub-agents:

1. **Planner Agent**: Analyzes the backlog and suggests a sprint plan based on target velocity.
2. **Risk Agent**: Identifies blockers, overdue tasks, and velocity slips.
3. **Workload Agent**: Analyzes team load and suggests rebalancing.
4. **Synthesizer**: Merges all sub-agent outputs into a final actionable report.

## RAG & Vector Memory

FRIDAY utilizes **pgvector** to ground agent knowledge in your actual project data. 

- **Knowledge Retrieval**: Before responding, the agent performs a similarity search across project documentation and issue history.
- **Session History**: Conversation logs are stored in `PmAiSession`, allowing the agent to remember context across multiple interactions in the same session.

## Observability with Langfuse

All agent activities are traced via **Langfuse**. This includes:
- Individual LLM generations (prompts and completions)
- Tool call arguments and outputs
- Graph node transitions
- Token usage and latency per step

You can view these traces in the **Traces** module (`/traces`).

## Building Custom MCP Tools

Register your own tools to extend agent capabilities:

```ts
// lib/ai/custom-tools.ts
import { MCP } from "@/lib/mcp/server";

MCP.registerTool({
  name: "summarizePR",
  description: "Reads a GitLab MR and returns an AI summary",
  parameters: {
    mrId: { type: "string", description: "MR ID to summarize" }
  },
  execute: async ({ mrId }) => {
    const mr = await fetchGitLabMR(mrId);
    return summarizeWithLLM(mr.description + mr.diff);
  }
});
```

Once registered, your tool is immediately available to any agent connected via the `/api/mcp` route.

## Architecture

```
Browser / Claude Desktop
        ↓ HTTP POST /api/mcp
MCP Route Handler (Next.js App Router)
        ↓ tool dispatch
Tool Implementations (tRPC routers / Prisma)
        ↓ DB queries
PostgreSQL
```

The MCP layer is thin by design — it maps tool calls directly to existing tRPC procedures, meaning any existing PM operation can be exposed as an MCP tool with minimal boilerplate.
